# Target versions

Fox-Grade ports mods *to* a target version. This is where that stands.

## Supported

A version is supported when a corpus has been run against it and the result is published. Having tables is most of
the work and none of the evidence.

| target | corpus | boots |
|---|---|---|
| 26.2 | 130 mods | 86 |
| 26.1.2 | 13 mods | 7 |
| 26.1 | 13 mods | 6 |

26.1 and 26.1.2 agree on twelve of their thirteen mods. The one difference is FerriteCore, which replaces vanilla's
blockstate cache and meets a real shape change between those releases — not a fault in the derived tables.

## Tables built, not supported

Thirty versions have derived tables: 1.14.4, 1.15.2, 1.16.5, 1.17.1, 1.18.2, 1.19.2, 1.19.4, the 1.20 line, the
whole 1.21 line, and the 26.1 line. `tools/add-target.py` builds them for any version in one command.

None of those below 26.1 can be offered yet, and the reason is not the tables.

## Why pre-26 versions are blocked

Fox-Grade remaps a mod's references to **Mojang names**. On 26.x that is exactly right: those jars ship
unobfuscated, and Mojang names are what Fabric loads at runtime. On every older version Fabric's runtime namespace
is **intermediary**, and Mojang names are a development convenience that resolves to nothing.

This is not a theory. A port built for 1.21.1 contains 622 Mojang-named references and no intermediary ones —
correct by the engine's own model, and unloadable on the version it was built for.

The access widener is the same fault seen from closer up. It declares the `official` namespace, which is Mojang
names on 26.x and obfuscated names everywhere else, so Fabric rejects the mod outright on 1.21.2 before anything
else can go wrong. Fixing the widener alone would move the failure later without moving it away.

So the work is a namespace decision that is currently made once and threaded through remapping, wideners, refmaps
and shims. Making it a property of the target — Mojang names for 26.x, intermediary below — is a considerable
change and should be started deliberately, not discovered halfway through a measurement run.

## Harness

`tools/make-instance.py <version>` builds everything one target needs to be measured: launch classpath, a world
generated by that version's own server jar (a client will not open a newer one), the Fabric API build for it, an
options file so the accessibility prompt does not swallow quickPlay, and the assetIndex read from the version
metadata. `tools/run-version.sh` then measures it under the same pass rule as every other lane.

`MEASURE_FLOOR=<version> ./build.sh` produces a jar that will load on a version it has not been measured on, so the
measurement can happen at all. It is not a jar to publish, and the build says so.
